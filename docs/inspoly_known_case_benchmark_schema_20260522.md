# InsPoly Known-Case Benchmark Schema

- Date: 2026-05-22
- Scope: sidecar-only stable benchmark corpus after Side/Outcome Phase 2 and Phase 4
- Runtime behavior changed: false
- Network/RPC required: false

## Purpose

The known-case corpus is a small, stable, machine-readable regression set. It exists to verify Side/Outcome semantics without replaying thousands of noisy local artifacts and without live/RPC access.

It is not a scorer tuning dataset and does not authorize Phase 3 capital-at-risk normalization, scoring weight changes, threshold changes, Strong Risk/HER/funding/candidate-admission changes, UI sorting/filtering changes, or storage changes.

## Corpus File

Default path:

`tests/fixtures/known_case_benchmark/post_side_outcome_known_cases.json`

The corpus root has:

- `reportType`: `post_side_outcome_known_case_benchmark_corpus`
- `schemaVersion`: `known_case_benchmark_v1`
- `sidecarOnly`: must be `true`
- `networkUsed`: must be `false`
- `productionIntegration`: must be `false`
- `runtimeBehaviorChanged`: must be `false`
- `summary`: source counts and required-category coverage
- `cases`: list of known cases

## Required Case Fields

Each case must include:

- `case_id`: stable machine-readable id.
- `source_type`: one of `real_local_artifact`, `generated_audit_evidence`, `review_packet`, or `synthetic_fixture`.
- `source_path`: local path that explains where the case came from.
- `mode`: `scanner`, `archive`, `event_forensic`, or `reconstruction`.
- `wallet`, `market`, `event`, `trade_key`: identifiers when available; use `unknown` only when the source lacks them.
- `raw_side`: raw order side, usually `BUY` or `SELL`.
- `raw_outcome`: raw token outcome, usually `YES` or `NO`.
- `raw_token_price`: raw token price as a decimal string or original percent string.
- `economic_side`: economic side after BUY/SELL inversion.
- `model_probability`: economic-side probability after Phase 2 semantics, or `unknown`.
- `cluster_direction`: normalized cluster direction after Phase 4 semantics, or `unknown`.
- `expected_phase2_effect`: expected probability/model semantic effect.
- `expected_phase4_effect`: expected cluster/same-side effect.
- `phase3_capital_status`: `not_applicable`, `blocked_overlap`, or another explicit blocked status.
- `sensitive_context`: boolean marker for Strong Risk/HER/funding/candidate-admission-adjacent context.
- `expected_result`: executable expectations used by the runner.
- `notes`: analyst-readable context.
- `provenance_quality`: explains whether the case is real, generated from audit evidence, review-packet-derived, or synthetic.

Optional fields:

- `derived_from_artifact`: real local artifact path when the case is copied from generated audit evidence.
- `quality_notes`: local audit quality notes.
- `case_trades`: list of row-level trade expressions for pair/cluster cases.
- `legacy_fields_present`: old-report fields used to prove absent-safe compatibility.

The fixture must cover:

- `sell_no_low_price_economic_yes_high_probability`

- `buy_no_sell_yes_same_cluster_long_no`

- `archive_affected_case`

- `stable_unaffected_control`

## Provenance Rules

Synthetic cases are allowed only when stable real local evidence is unavailable or too noisy. They must use `source_type: synthetic_fixture` and a `provenance_quality` value containing `synthetic`.

Generated audit evidence can reference real local artifacts, but it must not be presented as live proof. Use `derived_from_artifact` to point at the original local artifact path when available.

Review packets are acceptable stable local evidence because they were generated by earlier bounded sidecar audits and include explicit RFC expectation markers.

## Runner Contract

`tools/run_known_case_benchmark.py` checks:

- Phase 2 economic-side probability expectations.
- Phase 4 normalized cluster-direction expectations.
- malformed/missing rows remain `unknown`, not zero;
- old-report rows can be derived only from raw side/outcome/price;
- Phase 3 cases remain blocked and never become runtime-allowed;
- direct gate mutation remains forbidden.

Passing this corpus means local Side/Outcome regression coverage is ready for future quick checks. It does not close the separate live/RPC validation blocker for remembered Event Forensic weak-history near-certainty cases.

## 2026-05-26 V2 Addendum

`known_case_benchmark_v2` keeps the original Side/Outcome contract and adds advisory-only controls. New case fields:

- `assertion_type`: `side_outcome_contract`, `false_positive_control`, or `sidecar_context_control`.
- `expected_behavior`: what the case may prove.
- `forbidden_interpretation`: what the case must not be used to justify.
- `false_positive_notes`: compact notes for false-positive controls.
- `source_note`: source-quality context without importing bulky raw artifacts.

Additional source types are allowed for compact controls:

- `false_positive_library`
- `sidecar_measurement`

Additional required categories:

- `true_low_probability_later_winner`
- `weak_history_near_certainty_demotion`
- `selected_market_vs_whole_event_scope_boundary`
- `pagination_truncation_warning_control`
- `false_positive_near_certainty_control`
- `high_volume_public_user_false_positive_control`
- `funding_unknown_control`
- `no_independent_hard_evidence_control`

V2 controls are still sidecar-only. They do not authorize scoring, gate, routing, Phase 3, pagination, storage, or UI behavior changes.

## 2026-05-26 V3 Addendum

`known_case_benchmark_v3` keeps the v1/v2 contracts and adds public-source metadata for curated public-case controls.

New source types:

- `public_enforcement_source`
- `public_source_metadata`

New assertion levels:

- `exact_wallet_supported`
- `named_user_only`
- `pattern_level_only`
- `market_level_only`
- `local_artifact_supported`
- `sidecar_context_only`
- `synthetic_control`

New metadata fields:

- `source_urls`
- `source_titles`
- `source_dates`
- `evidence_quality`
- `assertion_level`
- `public_knowledge_timing`
- `catalyst_timing`
- `requires_fresh_validation`

Public-case controls must include source URL/title/date metadata and a `forbidden_interpretation`. They are advisory by default: `automatic_action_allowed`, `safe_to_use_for_scoring_claims`, and `exact_wallet_detection_allowed` must all be `false`.

Exact-wallet public cases require explicit source-backed wallet and market identity. If the source describes only a named user, unnamed cluster, article-level pattern, or market-level concern, the case must use `named_user_only`, `pattern_level_only`, or `market_level_only`; it must not assert exact-wallet detection.

Additional v3 categories:

- `public_maduro_enforcement_named_user_control`
- `public_maduro_pre_charge_market_timing_control`
- `public_iran_military_cluster_pattern_control`
- `public_zachxbt_axiom_pattern_control`
- `public_google_year_in_search_retrospective_control`
- `public_trump_whale_high_volume_control`

V3 still does not authorize scoring, gate, routing, Phase 3, pagination, storage, UI sorting/filtering, or runtime behavior changes.
